## HTTP 400 的实际原因

首次快速连续调用中，部分请求返回 400。旧执行器未读取非 200 响应正文，导致 CPA 只能显示状态码。本次补上了有界正文读取：最多 8 KiB、2 秒，保持原 HTTP 状态，不重发请求，并在返回客户端前隐藏凭据。

间隔 30 秒复测时，先前失败的四个模型均调用成功。随后对已验证模型追加最多四条短请求，第四条复现了上游明确的拒绝原因：

```json
{
  "error_code": "TM.00001041",
  "error_msg": "Concurrent chats have reached the upper limit (3). Close some chats and try again."
}
```

这是被测账号在测试时的上游聊天会话上限。短间隔的顺序调用也曾触发，不能将客户端顺序执行视为上游会话已经立即释放的保证。插件现在会透传这项原因，仍保留上游 HTTP 400。

继续核对官方 26.9.101 抓包与 26.9.102 内核代码，发现官方通过 `PUT /snap-manager/v1/chat-session/heartbeat?status=busy` 和 `status=idle` 管理会话占用；心跳与聊天使用相同的 `user-session-id`，busy 每 30 秒更新。原实现缺少这项生命周期通知。

本次补齐了该流程。每条请求使用插件新生成的独立 ID，完成、失败、取消后发送 idle；周期心跳的短暂失败不会提前释放仍在生成的聊天。测试没有使用或关闭用户已有的 VS Code 会话。

最终二进制在无人工等待间隔的情况下，连续完成三条福利模型非流式请求和一条福利模型流式请求，全部 HTTP 200，未再在第四次请求触发上限。三个模型分别为 `deepseek-v4-flash-0731`、`glm-5.3-flash`、`deepseek-v4-pro-0813`；流式检查使用 `deepseek-v4-flash-0731`。这验证了此次顺序调用场景，不代表绕过真实并发上限。

## 测试期间的上游模型目录变化

约北京时间 23:30，Agent Center 的五个智能体详情开始全部返回空模型列表，实时目录只剩三个福利模型。直接读取上游、使用修复前二进制、使用最终二进制三种方式得到相同结果；模型发现本身没有 HTTP 错误。

因此，前文七模型成功记录是早先真实调用的结果；最终时刻 CPA 按上游实时目录展示三个福利模型。没有为凑齐七个模型添加静态默认项，也没有据此断言普通模型已永久下线。后续可用列表以账号实际返回为准。

## 验证范围

- 真实订阅验证了单账号模型发现、早先七个模型的基础文本回答及普通/福利两类流式响应；会话修复后的最终包验证了当时仍在目录中的三个福利模型和连续四次调用。

- 请求设置 `max_tokens: 64`；部分模型上报的 `completion_tokens` 超过 64，并包含推理计数，因此该参数不应视为本次总生成用量的硬上限。
- 本地 `go test -race ./...`、`go vet ./...` 及完整 CPA 集成测试通过；覆盖错误正文透传、busy/idle 配对、短暂心跳失败、拒绝和超时后的释放，以及超过三个连续请求不泄漏会话占用。
- Linux 库在本地交叉编译，只上传二进制和专用测试脚本。最终包的四个 ABI 导出、ZIP 布局与 SHA-256 已检查；该产物最高引用的 glibc 符号版本为 `GLIBC_2.3.2`，被测服务器容器为 glibc 2.36。
